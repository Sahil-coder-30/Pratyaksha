Why a Chrome Extension — Strategic Rationale

The Problem Statement explicitly requires that sensitive data must NOT be shared with cloud providers. A browser extension is the only technology that satisfies all five PS constraints simultaneously.

🔒
Privacy Enforcement Point
Extensions run in the same process as the browser page but in an isolated world. They can intercept, analyze, and redact data before it ever reaches the network.
🧠
On-Device Intelligence
Extensions can host ML models (via WebGPU), run inference locally, and access the GPU without requiring native app installation — zero friction for the user.
🤖
DOM + Pixel Access
Extensions uniquely have access to both the page DOM (via content scripts) AND the visual pixel buffer (via captureVisibleTab) — enabling the dual-channel perception pipeline.

Manifest V3 Architecture — Key Changes

Manifest V3 (MV3) is the current and future standard for Chrome extensions. It introduces important architectural changes from MV2 that directly impact how PRATYAKSHA must be built. Understanding these constraints is critical for the team.

⚠️
Critical MV3 Constraint: Service Worker Lifecycle
In MV3, background pages are replaced by Service Workers. Service workers are ephemeral — they spin up on demand and can be killed by Chrome after ~30 seconds of inactivity. You CANNOT store state in global variables. All persistent state must go to chrome.storage or IndexedDB.
Background Page (MV2) → Service Worker (MV3)
Background scripts now run as ephemeral Service Workers. They wake up on events and sleep when idle. PRATYAKSHA's main orchestration logic lives in the Service Worker and must be designed to be stateless.
XMLHttpRequest → fetch() only
Service Workers only support the Fetch API. No XMLHttpRequest. All API calls to cloud services must use fetch(). This is fine — we use fetch + WebSocket for streaming.
Background DOM Access → Offscreen Documents
Service Workers have no DOM access and no WebGPU. For GPU-accelerated ONNX inference, we must use a Chrome Offscreen Document — a hidden HTML page that runs continuously and holds the WebGPU context.
Remote Code → Bundled Code Only
MV3 prohibits loading and executing remotely-hosted code. All JavaScript, ONNX models, and assets must be bundled within the extension package. Models are fetched from the extension's own CRX bundle or local CacheStorage.
webRequest (blocking) → declarativeNetRequest
Blocking webRequest API is removed. For URL filtering/blocking, use declarativeNetRequest with static rulesets. PRATYAKSHA doesn't need to block requests, but this matters for understanding the permission model.
Persistent Side Panel (new MV3 feature)
Chrome 114+ introduces the Side Panel API — a persistent UI panel attached to the browser window. PRATYAKSHA's main UI (task input, approval flow, action history) lives here. Accessible via chrome.sidePanel.
✅
PRATYAKSHA's MV3 Compatibility Strategy
Every PRATYAKSHA component has been designed specifically for MV3 constraints: Service Worker for event routing, Offscreen Document for WebGPU, IndexedDB for persistent Vault storage, Side Panel for persistent UI. No MV2 workarounds needed.

Extension Components — Deep Dive

Each extension component runs in a different execution context with different APIs, permissions, and lifecycle characteristics. Understanding these contexts is critical for correct implementation.

⚙️
Service Worker
background/service-worker.js

The main orchestrator. Runs ephemerally — wakes on events, sleeps when idle. Routes messages between all other contexts. Manages the cloud API session (JWT, WebSocket). Handles all chrome.* API calls that require extension permissions (tabs, storage, scripting). Must be stateless — all state persisted to chrome.storage.session.

chrome.runtimechrome.tabschrome.scriptingchrome.storage.sessionfetch()
🖥️
Offscreen Document
background/offscreen.html

A hidden HTML page created and managed by the Service Worker via chrome.offscreen.createDocument(). This is the only context in MV3 that has both a DOM and GPU access. Hosts all 4 ONNX models and the WebGPU inference session. Communicates via chrome.runtime.sendMessage(). Created once and kept alive for the session.

WebGPU APIONNX Runtime WebCanvas APIchrome.runtime.onMessage
📃
Content Script
content/content-main.js

Injected into every tab page (or specific URL patterns). Runs in an isolated world — has access to the page DOM but not page JS variables. Responsible for: DOM extraction (building the semantic node tree), executing DOM events on behalf of the Agent Runner, and observing DOM mutations for change detection.

document DOMMutationObserverdispatchEvent()chrome.runtime.sendMessage
💻
Side Panel
sidepanel/panel.html

The primary user interface. A persistent panel attached to the browser window (Chrome 114+). Contains: task input textarea, real-time action preview stream, step-by-step approval buttons, vault status indicator, and action history log. Communicates with the Service Worker via chrome.runtime.sendMessage().

chrome.sidePanelchrome.runtimeVanilla JS DOM
🔒
Vault Service
vault/vault-service.js

A pure-JS class shared across contexts (loaded in Service Worker and Offscreen Document). Manages the IndexedDB pratyaksha_vault database. Exposes three core methods: tokenize(piiValue, type) → token, rehydrate(token) → piiValue, purgeSession(). All data encrypted with AES-256-GCM before write.

IndexedDBWeb Crypto APIAES-256-GCMPBKDF2
🤖
Agent Runner
agent/agent-runner.js

Loaded via chrome.scripting.executeScript() into the target tab. Receives rehydrated action plans and executes them step-by-step: clicking elements, typing text, scrolling, waiting for assertions. Maintains a rollback stack. Dispatches CustomEvent('pratyaksha:step-done') after each step for the UI to consume.

Message Passing Protocol

Chrome extensions use a strict message passing model between contexts. All inter-context communication goes through chrome.runtime.sendMessage() (one-shot) or chrome.runtime.connect() (persistent port). PRATYAKSHA uses a typed message protocol to keep all communication clear and auditable.

// Typed Message Protocol — all messages follow this schema const MessageTypes = { // Side Panel → Service Worker START_TASK: 'START_TASK', // { task: string } CANCEL_TASK: 'CANCEL_TASK', // { task_id: string } APPROVE_STEP: 'APPROVE_STEP', // { step_index: number } REJECT_STEP: 'REJECT_STEP', // { step_index: number, reason: string } GET_VAULT_STATUS: 'GET_VAULT_STATUS', // {} — returns token count, size // Service Worker → Side Panel (via port) TASK_STARTED: 'TASK_STARTED', // { task_id: string } STEP_PENDING: 'STEP_PENDING', // { step: ActionStep, reasoning: string } STEP_DONE: 'STEP_DONE', // { step_index, success, latency_ms } TASK_COMPLETE: 'TASK_COMPLETE', // { task_id, total_steps, duration_ms } ERROR: 'ERROR', // { code, message, step_index? } // Service Worker → Offscreen Document RUN_VISION: 'RUN_VISION', // { imageDataUrl: string } VISION_RESULT: 'VISION_RESULT', // { sceneGraph: SceneGraph, sanitizedDataUrl: string } // Service Worker → Content Script EXTRACT_DOM: 'EXTRACT_DOM', // {} — triggers DOM extraction EXECUTE_ACTION: 'EXECUTE_ACTION', // { action: RehydratedAction } };
🔄 Typical Task Execution Message Flow
  1. User types task in Side Panel → sends START_TASK to Service Worker
  2. Service Worker calls chrome.tabs.captureVisibleTab() → gets screenshot DataURL
  3. Service Worker sends RUN_VISION to Offscreen Document with screenshot
  4. Offscreen Document runs 4 ONNX models → returns VISION_RESULT with scene graph
  5. Service Worker sends EXTRACT_DOM to Content Script → gets DOM node tree
  6. Service Worker calls Vault Service: tokenize all PII in scene graph + DOM
  7. Service Worker sends sanitized canvas + tokenized scene graph to Cloud Orchestrator
  8. Cloud Orchestrator streams action plan via WebSocket → Service Worker receives steps
  9. For each step, Service Worker sends STEP_PENDING to Side Panel for user approval
  10. User approves → Service Worker calls Vault Service to rehydrate tokens → sends EXECUTE_ACTION to Content Script
  11. Content Script dispatches real DOM events → returns success/failure
  12. Service Worker sends STEP_DONE to Side Panel → loop continues

Screen Capture Pipeline

Screen capture is the first step of the perception pipeline. PRATYAKSHA uses chrome.tabs.captureVisibleTab() — the only Chrome API that captures a high-fidelity screenshot of the current tab without requiring screen sharing permission from the user.

✅
Privacy Advantage
chrome.tabs.captureVisibleTab() does NOT trigger the browser's screen sharing permission dialog. It is a silent, extension-internal API that captures only the active tab, not the entire screen or other apps. This is crucial for a low-friction privacy-preserving workflow.
// service-worker.js — Screen capture pipeline async function captureAndProcess(tabId) { // Step 1: Capture the visible tab as JPEG (quality 90 = good quality, smaller size) const imageDataUrl = await chrome.tabs.captureVisibleTab(null, { format: 'jpeg', quality: 90 }); // Step 2: Send to Offscreen Document for ONNX inference (never sent to network) const visionResult = await sendToOffscreen({ type: 'RUN_VISION', payload: { imageDataUrl } // stays inside extension process }); // Step 3: Vault tokenizes PII, returns sanitizedDataUrl (PII blacked out) const { sanitizedDataUrl, tokenizedSceneGraph } = await vaultService.sanitize( visionResult.sceneGraph, visionResult.rawCanvas // raw canvas only exists inside extension ); // ONLY sanitizedDataUrl and tokenizedSceneGraph leave the extension return { sanitizedDataUrl, tokenizedSceneGraph }; }
⚠️
Handling Non-DOM Content (The Core PS Problem)
PDFs rendered via Chrome PDF Viewer, embedded images in forms, canvas-rendered content (DigiLocker documents), and SVG infographics are invisible to DOM extraction. The pixel capture + ONNX pipeline is the only way to read these. This is why the Vision Worker is non-optional, not a nice-to-have.
🗺️

DOM Extraction Strategy

The DOM extractor builds a compact, structured representation of the page that the cloud Orchestrator can reason about to identify actionable elements (buttons, inputs, links) without access to the full page HTML (which might contain PII in text).

// content/dom-extractor.js — Builds a clean, safe semantic node tree function extractSemanticTree() { const INTERACTIVE = ['a', 'button', 'input', 'select', 'textarea']; const SEMANTIC = ['h1','h2','h3','label','p','span','td','li']; return [...document.querySelectorAll([...INTERACTIVE, ...SEMANTIC].join(','))] .filter(el => el.getBoundingClientRect().width > 0) // visible only .map(el => { const rect = el.getBoundingClientRect(); return { tag: el.tagName.toLowerCase(), role: el.getAttribute('role') || null, aria: el.getAttribute('aria-label') || null, text: el.innerText?.slice(0, 120), // NOTE: PII scanner runs on this text type: el.type || null, // for input elements name: el.name || null, selector: buildUniqueSelector(el), // CSS selector for Agent Runner bbox: { x: rect.x, y: rect.y, w: rect.width, h: rect.height }, visible: true }; }); }
💡
PII Scanner on DOM Text
All text fields in the extracted node tree are passed through the PII scanner before being included in the tokenized scene graph. Any Aadhaar/PAN numbers or phone numbers found in DOM text are replaced with tokens in the JSON sent to the cloud, even if the Vision Worker didn't detect them visually.

WebGPU in Chrome Extension — Implementation

WebGPU gives PRATYAKSHA direct access to the GPU for inference without any native drivers or plugins. It is the key technical enabler for sub-200ms on-device vision inference inside the browser.

⚠️
Service Worker Cannot Use WebGPU
The MV3 Service Worker runs in a Web Worker context without a DOM or GPU context. All WebGPU calls must happen inside the Offscreen Document, which is a full HTML page with a rendering context. The Service Worker creates the Offscreen Document once on startup and uses message passing to send work to it.
// vision/vision-worker.js — Runs inside offscreen.html let ort, sessions = {}; async function initModels() { // Import ONNX Runtime Web (bundled in extension package) ort = await import('../lib/ort.webgpu.min.js'); // Prefer WebGPU, fall back to WASM if unavailable (e.g., low-end devices) ort.env.wasm.numThreads = 4; const options = { executionProviders: ['webgpu', 'wasm'], // webgpu first, wasm fallback graphOptimizationLevel: 'all', enableCpuMemArena: false, }; // Load model weights from extension bundle (no network request) sessions.face = await ort.InferenceSession.create('./models/yolov8n-face-int8.onnx', options); sessions.textDetect = await ort.InferenceSession.create('./models/dbnet-small-int8.onnx', options); sessions.ocr = await ort.InferenceSession.create('./models/indic-crnn-int8.onnx', options); sessions.classify = await ort.InferenceSession.create('./models/mobilenetv4-tiny-int8.onnx', options); postMessage({ type: 'MODELS_READY' }); } // Handle vision request from Service Worker chrome.runtime.onMessage.addListener(async (msg) => { if (msg.type === 'RUN_VISION') { const { imageDataUrl } = msg.payload; const imageBitmap = await decodeImage(imageDataUrl); const [faces, textRegions, classification] = await Promise.all([ runFaceDetection(sessions.face, imageBitmap), runTextDetection(sessions.textDetect, imageBitmap), runClassification(sessions.classify, imageBitmap), ]); // OCR runs on detected text regions only (not whole image) const ocrResults = await runOCR(sessions.ocr, imageBitmap, textRegions); return { sceneGraph: buildSceneGraph(faces, textRegions, ocrResults, classification) }; } });

Vault & Privacy Layer

The Vault Service is the privacy enforcement centrepiece of PRATYAKSHA. It is responsible for converting raw PII into opaque tokens before data leaves the local context, and converting tokens back to real values for action execution.

// vault/vault-service.js — Core Vault implementation class VaultService { constructor() { this.db = null; this.encKey = null; this.sessionId = crypto.randomUUID(); } async init(userPin) { // Derive AES-256-GCM key from user PIN + device fingerprint const salt = await getDeviceFingerprint(); const keyMaterial = await crypto.subtle.importKey('raw', new TextEncoder().encode(userPin), 'PBKDF2', false, ['deriveKey']); this.encKey = await crypto.subtle.deriveKey({ name: 'PBKDF2', salt, iterations: 300000, hash: 'SHA-256' }, keyMaterial, { name: 'AES-GCM', length: 256 }, false, ['encrypt', 'decrypt']); this.db = await openIndexedDB('pratyaksha_vault', 1); } async tokenize(piiValue, type) { // Generate unique session-scoped token const count = await this.countByType(type); const token = `⟨${type}_${String(count + 1).padStart(2,'0')}⟩`; // Encrypt PII value before storing const iv = crypto.getRandomValues(new Uint8Array(12)); const encrypted = await crypto.subtle.encrypt( { name: 'AES-GCM', iv }, this.encKey, new TextEncoder().encode(JSON.stringify({ piiValue, type })) ); await this.db.put('tokens', { token, encrypted, iv, sessionId: this.sessionId }); return token; // ONLY the token leaves this function } async rehydrate(token) { const record = await this.db.get('tokens', token); if (!record) throw new Error(`VAULT_ERROR: Unknown token ${token} — action blocked`); const decrypted = await crypto.subtle.decrypt( { name: 'AES-GCM', iv: record.iv }, this.encKey, record.encrypted ); return JSON.parse(new TextDecoder().decode(decrypted)).piiValue; } }

Side Panel UI Design

The Side Panel is the primary user-facing interface. It must be clean, reassuring, and give the user clear visibility and control over everything the AI is doing. The design follows the principle: "Show your work, ask before acting."

📝 Task Input View
  • Large text area for natural language task description
  • Context badge showing current page domain
  • Vault status indicator (green = active, how many tokens stored)
  • Privacy mode toggle (strict / standard)
  • "Start Agent" primary CTA button
  • Recent task history (last 5 tasks)
⏳ Execution View (Active Task)
  • Real-time AI reasoning trace (collapsible)
  • Current step card: action type + target element + value (tokens shown, never real PII)
  • Large "Approve ✅" and "Skip ⏭" buttons for each step
  • "Stop Agent 🛑" emergency button (always visible)
  • Progress bar: steps done / total estimated
  • Live DOM highlight of the element being targeted
📜 History & Audit View
  • Chronological log of all past agent actions
  • Each entry: timestamp, domain, action type, success/fail badge
  • Expand each entry to see the full reasoning trace
  • "Undo Last Task" button (triggers rollback stack)
  • "Clear All History" (calls /ledger/history DELETE)
🔒 Vault View
  • Summary: N faces, N Aadhaar numbers, N PAN cards detected this session
  • Token list: shows token names (e.g., ⟨AADHAAR_01⟩) but never real values
  • "Lock Vault" button: encrypts and clears session keys from memory
  • "Clear Session Vault" button: purges all IndexedDB records
  • Session duration + total PII items protected this session

Build & Distribution

The extension is built using a minimal Vite config (for bundling only — no framework). The build output is a clean MV3-compliant extension directory that can be loaded unpacked in Chrome or submitted to the Web Store.

🛠️ Build Tooling
  • Bundler: Vite + CRXJS plugin (Chrome extension aware bundler)
  • Language: Vanilla JS (ES2022 modules) — no TS for now (faster iteration)
  • Model bundling: ONNX files copied to dist/models/ as-is
  • Hash generation: SHA-256 hashes of model files auto-generated at build time for integrity check
  • Dev mode: vite build --watch + Chrome 'load unpacked' for instant reload
🏦 Chrome Web Store Submission
  • All permissions justified in the submission form with specific use case per permission
  • Privacy Policy document (in English + Hindi) linked in the store listing
  • Remote code execution: explicitly None (all code bundled)
  • Single purpose statement: "Privacy-preserving on-device browser automation"
  • For Enterprise internal deployment: enterprise policy-based force-install (no store needed)
🔧 Pre-Release Security Checklist
All ONNX model SHA-256 hashes embedded in extension code
CSP header blocks all inline scripts and external script sources
IndexedDB Vault encrypted with AES-256-GCM (verified by unit test)
No PII logged to console.log() in any file (grep-verified at build)

WebSocket connection uses WSS with cert pinning via Cloudflare

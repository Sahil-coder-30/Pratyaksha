High-Level Design
PRATYAKSHA Architecture

A production-grade, privacy-first, microservices architecture for on-device visual perception, agentic browser automation, and secure cloud reasoning. Zero raw PII ever crosses the local boundary.

🔩 8 Microservices 🔐 Zero-Trust Security ⚡ WebGPU Inference 🌐 Manifest V3 Extension 📦 ONNX Runtime Web ☁️ Hybrid Cloud / Edge
🏛️

System Overview — The Big Picture

PRATYAKSHA is a hybrid local-cloud system. The most privacy-sensitive computation — screen capture, vision inference, and PII de-identification — is performed entirely inside the Chrome browser using WebGPU-accelerated ONNX models. Only a sanitized, token-substituted representation of the screen is sent to cloud services for high-level reasoning.

🔐
The Core Privacy Contract
Raw screenshots, biometric data (faces), and Aadhaar/PAN numbers are NEVER transmitted outside the browser extension. The Vault service pseudonymises all PII before anything crosses the local boundary. The cloud sees only tokens like ⟨FACE_001⟩ and ⟨AADHAAR_01⟩.

Microservices Inventory

PRATYAKSHA decomposes into 8 discrete services across two deployment zones: the browser-local layer (running inside the Chrome extension service worker and offscreen document) and the cloud compute layer (Docker containers on Kubernetes). Each service owns its data, exposes a versioned API, and can be deployed and scaled independently.

7-Step Data-Flow Architecture

Every PRATYAKSHA request follows a strict 7-step pipeline. Steps 1–3 are executed locally; steps 4–5 happen in the cloud (with only sanitized data); steps 6–7 rehydrate tokens back to real values locally before the agent acts.

📸 Step 1 — PERCEIVE: Dual-Channel Screen Understanding
Channel A — DOM Extraction: The content script enumerates all interactive and semantic DOM nodes (inputs, buttons, headings, paragraphs, tables), extracting text content, ARIA labels, bounding boxes, and computed styles to produce a structured node tree.

Channel B — Pixel Capture: chrome.tabs.captureVisibleTab() captures the current viewport as a high-resolution PNG. This is passed directly to the Vision Worker — it NEVER leaves the local context before sanitization.

Non-DOM Content (Key Innovation): PDFs rendered by the browser, embedded iframes, canvas elements, and SVG infographics cannot be read by DOM extraction alone. The Vision Worker's pixel pipeline handles these via the OCR + detection stack — this is the core problem this PS solves.
👁️ Step 2 — DETECT: Vision Worker Model Pipeline
The Vision Worker runs 4 models in sequence, each taking ~30 ms on WebGPU (total ~120 ms):

① Face Detector — YOLOv8-nano INT8: Detects all faces, produces bounding boxes. All detected faces are registered as ⟨FACE_N⟩ tokens in the Vault.
② Text Region Detector — DBNet-small: Detects all text regions including regions inside images/PDFs that DOM can't reach.
③ Indic OCR — CRNN with Devanagari + Latin: Reads text from detected regions. Pattern-matches against PII regexes (Aadhaar: 12-digit, PAN: AAAAA-9999-A, phone numbers, bank accounts).
④ Content Classifier — MobileNetV4-tiny: Classifies screen context (BANKING, MEDICAL, GOVERNMENT, GENERAL) to apply appropriate sanitization policy level.
🔒 Step 3 — SANITIZE: The Vault Service in Action
A. Image Redaction: Draws solid-colour fills (distinct per category: orange for faces, blue for Aadhaar, red for financial) over each detected PII bounding box on the captured canvas. The redacted canvas is what gets transmitted.

B. Token Registry: For each detected PII item, generates a deterministic session-scoped token (e.g., ⟨AADHAAR_01⟩). Stores token → {realValue, boundingBox, type, confidence} in AES-256-GCM encrypted IndexedDB. Replaces real values in the scene graph JSON with their tokens.

Output: A sanitized canvas (PNG) + a tokenized scene graph (JSON). These are the only artefacts that cross the local boundary.
🧠 Steps 4–5 — REASON + PLAN: Cloud Intelligence Loop
The sanitized canvas + tokenized scene graph are sent to the Cloud VLM Reasoner via HTTPS POST through the API Gateway. The VLM returns structured understanding (layout, semantics, actionable elements — all referencing tokens, not real data). The Agent Orchestrator runs a LangGraph planning loop to produce a JSON Action Plan: a sequence of typed actions — CLICK(selector), TYPE(token_or_literal), SCROLL(delta), WAIT(ms), ASSERT(condition). The Policy Engine intercepts the plan before it is returned, checking each action against OPA rules.
🔄 Steps 6–7 — REHYDRATE + EXECUTE: Local Action
The Action Plan arrives at the local Agent Runner still using tokens. The Vault Service is queried for each token to substitute the real value back — this happens entirely locally. The cloud never learns the real values. If a token is not found (tampered plan or hallucinated token), the action is blocked and the user is alerted. Rehydrated actions are then dispatched as real DOM events: dispatchEvent(new MouseEvent('click', ...)), dispatchEvent(new InputEvent('input', ...)), with each step logged to the local audit ledger and optionally synced (token-based) to the cloud ledger.

Security Architecture

PRATYAKSHA is designed against the OWASP Top 10, India's DPDP Act 2023, and relevant Enterprise data classification policies. Security operates at three levels: threat identification, technical controls, and verification/audit.

🔴 Threat Model
Malicious cloud provider sniffing screen data
Extension-to-extension XSS / message injection
Supply chain attack on ONNX model weights
Prompt injection via malicious web page content
Rogue action plan from compromised cloud service
IndexedDB vault exfiltration by other extensions
MitM on sanitized canvas upload (intercept + reassembly)
🟢 Technical Controls
Vault encrypts all PII with AES-256-GCM before IndexedDB write
Strict CSP: script-src 'self' — no inline scripts
ONNX model weights verified by SHA-256 hash on every load
Content sanitizer strips all HTML from page text before VLM prompt
Action plans validated against JSON Schema before execution
Isolated world content scripts (chrome API boundary enforced)
All cloud comms over TLS 1.3 with certificate pinning
🔵 Verification & Audit
Every action logged to immutable Ledger (token-based)
Policy Engine (OPA) audits every action plan before execution
User can review full session history in Side Panel
Destructive actions always require explicit user confirmation
Monthly automated security scan via Snyk + Dependabot
DPDP Act 2023 compliance — right to erasure via API
⛔
Hard Security Invariants — Must NEVER Be Violated
1. Raw captured screenshots are never sent over any network.
2. The PII ↔ Token mapping table never leaves IndexedDB (no sync, no backup to cloud).
3. The extension never auto-executes actions for banking/medical sites without user confirmation, regardless of policy verdict.
4. Model weight integrity check failure = fail-closed (refuse to process, alert user immediately).

Data Storage Design

PRATYAKSHA uses a split storage strategy: sensitive data stays entirely local (browser); anonymized telemetry and audit logs go to cloud. No cloud database ever holds real PII.

🔒
Local Vault Store
IndexedDB · Browser-only

Stores encrypted PII-to-token mappings. AES-256-GCM with key derived from device fingerprint + user PIN via PBKDF2 (300k iterations). Session-scoped by default: tokens expire with the browser session. Schema versioned for safe migration.

IndexedDB + Web Crypto APIAES-256-GCM
🔴
Token Cache
Redis · Cloud

Short-lived server-side cache for session tokens (JWT rotation, rate-limit counters, in-flight task state). Contains ZERO PII — only session identifiers, task IDs, and action plan drafts. All keys have TTL ≤ 24h.

Redis 7 (ElastiCache)TTL-based eviction
🗃️
Audit Ledger
PostgreSQL · Cloud

Stores per-user audit records of all agent actions: action_type, domain, timestamp, policy_verdict, success/failure. ALL values are token-based or anonymised. Indexed on user_id + timestamp. Soft-deletable for DPDP compliance.

PostgreSQL 16 (RDS)Event Sourcing
📈
Telemetry Store
TimescaleDB · Cloud

Time-series storage for anonymised performance metrics: per-model inference latencies, task success rates, policy block rates, daily active users. Feeds the Grafana dashboard. Raw events not stored beyond 24h.

TimescaleDB (PostgreSQL)Continuous Aggregation

⚡ Horizontal Scaling — Orchestrator
Kubernetes HPA scales svc-orchestrator from 2 → 8 pods based on CPU (target 70%) and custom RabbitMQ queue depth metric. Each pod is stateless — task state stored in Redis. P95 latency budget: 500ms for planning step. Load tested to 5,000 concurrent tasks.
🔁 Circuit Breakers & Fallbacks
If the Cloud VLM Reasoner is unavailable, the system falls back to DOM-only analysis (skipping visual understanding). If the Policy Engine is unreachable, the system fails-closed — no actions are executed without a policy verdict. All fallback paths are logged and surfaced to the user.
📦 Model Caching Strategy
ONNX model files (~45 MB combined) are cached in Chrome's CacheStorage API on first install. Subsequent sessions load from cache in <100ms. Model updates are version-controlled and only re-downloaded when the extension updates. SHA-256 integrity verified on every load.
🌍 Multi-Region Readiness
Primary in ap-south-1 (Mumbai) for Enterprise data residency compliance, failover to ap-southeast-1 (Singapore). PostgreSQL uses RDS Multi-AZ. Redis uses ElastiCache cluster mode with cross-AZ replication. RTO: 5 minutes, RPO: 0 (synchronous replication).

Architecture Decision Records (ADRs)

Key architectural decisions are documented here to preserve the reasoning behind each choice. This prevents re-litigating settled decisions and helps new team members understand the why, not just the what.

ADR-001
Use ONNX Runtime Web + WebGPU for on-device vision inference
✅ Decided
Context: Need to run face detection, text detection, and OCR inside the browser without native software installation. Decision: ONNX Runtime Web with WebGPU execution provider. Models are quantized to INT8. Alternatives rejected: TensorFlow.js (larger bundle, slower), WebNN (insufficient browser support in 2024), native app (breaks the browser-extension requirement). Trade-off: ~45 MB model bundle on first load; mitigated by CacheStorage caching.
ADR-002
Store PII vault in IndexedDB with AES-256-GCM (not chrome.storage)
✅ Decided
Context: Need to store PII-to-token mappings securely, locally. Decision: IndexedDB with Web Crypto API (AES-256-GCM). Key derived via PBKDF2 from device fingerprint + user PIN. Alternatives rejected: chrome.storage.local (not encrypted, may sync to Google servers in sync mode), localStorage (size limit, not encrypted). Trade-off: Higher implementation complexity; mitigated by an encapsulated Vault Service class.
ADR-003
Use LangGraph for cloud agentic orchestration (not custom FSM)
✅ Decided
Context: Need a robust, debuggable agentic loop for planning multi-step browser actions. Decision: LangGraph with an explicit state graph. Each node = one planning step. Edges represent conditional transitions. Alternatives rejected: Raw LLM loop (no state management, hard to debug), AutoGen (too opinionated, heavy). Trade-off: Python-only; mitigated because Orchestrator service is isolated behind an API.
ADR-004
Use Open Policy Agent (OPA) as the authorization sidecar
✅ Decided
Context: Need flexible, auditable policy enforcement for agent actions. Decision: OPA with Rego policies, deployed as a sidecar to svc-orchestrator. Policies stored in git and hot-reloaded via OPA bundle server. Alternatives rejected: Hardcoded if/else logic (not auditable), XACML (too complex). Trade-off: Additional ~5ms latency per decision; acceptable given security benefit.
ADR-005
Offscreen Document for WebGPU Vision inference context isolation
🔵 Proposed / Under Review
Context: Chrome Manifest V3 Service Workers cannot directly access WebGPU (no GPU context). Need a persistent GPU context for ONNX models. Proposed: Use chrome.offscreen.createDocument() with a dedicated HTML page holding the WebGPU context and ONNX session. Risk: Offscreen documents (Chrome 109+) have some lifecycle edge cases. Mitigation: Fallback to WASM execution provider on WebGPU failure.

Build Roadmap — Sprint Plan

The project is divided into 4 phases aligned with PRATYAKSHA evaluation milestones. Each phase delivers a demonstrable working increment.

Phase 1 — Foundation (Weeks 1–3) · Local Pipeline MVP
Set up Extension Shell (Manifest V3). Implement chrome.tabs.captureVisibleTab() + DOM extraction pipeline. Integrate ONNX Runtime Web + YOLOv8-nano face detector (WebGPU). Build Vault Service with IndexedDB + AES-256-GCM. Deliverable: A working extension that captures a screenshot, detects faces, and generates a tokenized scene graph locally.
Phase 2 — Full Vision Stack (Weeks 4–6) · All 4 Models
Add DBNet text detector, Indic CRNN OCR, and MobileNetV4 content classifier. Build the model orchestration pipeline in the Offscreen Document. Implement PII regex engine. Add sanitized canvas redaction. Test against government document PDF renders, bank portals, DigiLocker. Deliverable: Full local vision pipeline with privacy redaction working on real government portals.
Phase 3 — Cloud Intelligence (Weeks 7–9) · Full Agentic Loop
Deploy svc-orchestrator (FastAPI + LangGraph), svc-vlm-cloud (Gemini adapter), svc-policy (OPA), svc-analytics. Implement WebSocket streaming for action plans. Build Agent Runner with DOM event dispatch + rollback stack. Build approval UI in Side Panel. Deliverable: Full end-to-end agent loop — describe a task, approve, watch it execute safely.
Phase 4 — Polish & Evaluation (Weeks 10–12) · Production Ready
Performance optimization (sub-200ms local pipeline). Security hardening (Snyk scan, CSP audit, cert pinning). Accessibility (ARIA labels, keyboard navigation). Grafana dashboard + monitoring. User study with Security Evaluators. Chrome Web Store submission prep. Demo video production. Deliverable: Submission-ready product with full documentation and live demo.
